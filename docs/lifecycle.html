React 개발서버가 뜰 때 실제로 일어나는 일

그리고 소스 위치를 얻기 위해 어디에 끼어들 수 있는가 — react-code-locator v2 설계 노트

한 줄 요약

부팅 시점에 컴파일이 아예 없는 건 아니다 — 설정 파일, 의존성 사전 번들, 그리고 import 수집용 소스 스캔은 일어난다. 하지만 서빙용 변환(transform)은 0회다(1.3에서 실측). 실제 변환은 브라우저가 모듈을 요청한 뒤에야 일어난다.

그래서 "부팅 때 한 번 끼어든다"는 그림은 성립하지 않고, 모듈 파이프라인에 상주해야 한다.

1Vite @vitejs/plugin-react

1.1프로세스 부팅 — 설정 확정

vite 명령이 뜨면 createServer()가 순서대로 이걸 한다.

vite.config.ts 로드 (esbuild로 즉석 번들 → 실행)
   ↓
플러그인 배열 평탄화, enforce(pre / 없음 / post)로 정렬
   ↓
각 플러그인의 config(config, env) 훅 호출     ← 설정을 고칠 마지막 기회
   ↓
설정 병합 확정 (ResolvedConfig)
   ↓
각 플러그인의 configResolved(config) 훅 호출  ← 읽기만. 고치면 안 됨
   ↓
플러그인 컨테이너 생성 → buildStart()
   ↓
configureServer(server) 훅 호출               ← 미들웨어 등록
실측으로 알게 된 것

config()에서 plugin-react의 옵션 객체를 직접 고치는 건 안 통한다. plugin-react가 자기 옵션을 클로저에 캡처해버리기 때문이다.

대신 공식 확장점이 있다 — plugin-react는 config.plugins 전체를 훑어 plugin.api.reactBabel을 가진 플러그인을 모으고, 자기 Babel 옵션을 넘겨 호출한다. 우리는 여기에 Babel visitor를 심는다. 사용자는 react({ babel: … })를 쓸 필요가 없다.

1.2의존성 사전 번들 (optimizeDeps) — 사전 컴파일은 있다

"브라우저가 뜨기 전엔 아무것도 컴파일 안 한다"는 틀렸다. 세 가지가 컴파일된다.

  • vite.config.ts 자체 — esbuild로 즉석 번들해서 실행한다.
  • 스캐너가 사용자 소스를 파싱한다 — entry(index.html)에서 esbuild로 import 그래프를 훑는다. 목적은 딱 하나, bare import 특정 수집(react, lodash …). 결과물은 버린다.
  • 수집된 node_modules 패키지를 실제로 번들해 디스크에 쓴다 — CJS→ESM 변환과 요청 수 폭발 방지.

즉 사전 번들의 대상은 라이브러리다. 당신의 src/**는 스캔만 당하고, 서빙용 변환은 겪지 않는다.

1.3listen — 그리고 정지

서버가 포트를 열고 멈춘다. playground/vite/probe-boot.mjs가 서버를 띄운 뒤 HTTP 요청을 단 한 건도 보내지 않고 4초를 기다려 실측한 결과:

실측에서 읽어야 할 것 세 개

1. transform이 0회다. 사용자 소스가 plugin-react의 Babel을 타는 일은 요청 전에 없다. 훅 D·E는 부팅 시점에 발동할 수 없다 — 끼어들 파싱 자체가 존재하지 않는다.

2. 훅 C는 부팅 시점에도 발동한다. resolveId 로그가 증거다 — 스캐너도 플러그인 resolveId를 태운다. 예상 밖이었지만 무해하다(스캔 결과는 서빙에 쓰이지 않는다).

3. 사전 번들 결과는 deps/가 아니라 deps_temp_*에 있다. 커밋 시점에 deps/로 rename되고, 서버를 닫으면 temp가 정리된다. 그래서 close() 뒤에 deps/를 보면 비어 있고, "사전 번들이 없다"고 잘못 읽게 된다.

1.4첫 요청 — HTML

GET /
  → index.html 읽기
  → transformIndexHtml 훅          ← 스크립트 주입 지점 (우리 클라이언트 런타임)
  → <script type="module" src="/src/main.tsx"> 를 본 브라우저가 다시 요청

1.5모듈 파이프라인 — 요청 하나당 한 바퀴

GET /src/main.tsx
   ↓
resolveId(id, importer)        ★ C  어느 실제 파일로 볼 것인가
   ↓                                여기서 다른 모듈로 갈아치울 수 있다
load(id)                            디스크에서 문자열로
   ↓
transform(code, id)                 enforce 순서대로 체인
   ↓
결과 캐시 + 브라우저로 전송
훅 C를 쓰는 이유

react/jsx-dev-runtime 요청이 들어오면 우리 모듈로 돌린다. 대안인 jsxImportSource(tsconfig 설정)와 비교하면 — 사용자 설정 파일을 안 건드리고, emotion·theme-ui가 이미 그 자리를 점유했을 때 충돌하지 않는다. 우리 모듈 자신의 import는 importer를 검사해 통과시켜 순환을 막는다.

1.6plugin-react 내부에서 벌어지는 일

여기가 핵심이다. plugin-react는 JSX 변환을 자기가 하지 않는다.

plugin-react의 config() 반환값:
    { esbuild: { jsx: "automatic" } }     ← JSX 변환은 esbuild에 위임

plugin-react의 transform():
    Babel 실행
      ├ TypeScript 문법 제거
      ├ fast-refresh 프리앰블 주입   ← 파일 맨 앞에 약 19줄
      └ 우리 visitor (api.reactBabel)  ★ D   ← AST를 그대로 받는다
    ↓ codegen → 문자열
    ↓
Vite 내장 esbuild transform
      └ JSX → jsxDEV(...) 변환, __source 계산
실측 — 설계를 뒤집은 발견

Babel이 프리앰블 19줄을 앞에 붙인 뒤에 esbuild가 JSX를 변환한다. esbuild는 자기가 받은 문자열 기준으로 줄을 세므로, __source.lineNumber가 정확히 19줄 밀린다. (실제 5번째 줄 → lineNumber: 24)

"컴파일러가 계산한 값이니 정확하다"는 전제는 틀렸다. 정확한 조건은 따로 있다 — 파싱과 JSX 변환 사이에 코드가 움직이지 않을 것. Next의 SWC는 한 패스라 만족하고, Vite의 Babel→esbuild 파이프라인은 만족하지 않는다.

그래서 Vite에서는 훅 D가 JSX 위치까지 담당한다. AST의 원본 loc을 쓰므로 구조적으로 밀릴 수 없다.

1.7브라우저 실행 — 폭포수

main.tsx가 실행되며 자기 import를 요청하고, 그게 또 자기 import를 요청한다. 도달한 모듈만 1.5의 파이프라인을 탄다. 안 열어본 lazy 라우트는 서버가 존재조차 모른다.

1.8HMR

파일 저장 → chokidar 감지 → 모듈 그래프에서 영향받는 모듈 계산
  → 해당 모듈만 transform 재실행 (★ C·D 다시 발동)
  → WebSocket으로 브라우저에 push → 그 모듈만 재실행 → 리렌더 (★ G 다시 발동)

즉 훅 C·D·G는 일회성이 아니라 편집할 때마다 다시 돈다. 그래서 비용이 싸야 한다.

webpack 모드의 함정

App Router는 top-level resolve.alias가 아니라 module rule 레이어별 resolve.alias로 React를 해석한다 (app-pages-browser, react-server-components …). 그리고 rule 단위가 top-level을 이긴다.

따라서 module.rules / oneOf / rules를 재귀로 훑어 각 rule에도 alias를 넣어야 한다.

2.4SWC와 훅 D의 부재

Next는 SWC로 컴파일한다. SWC는 JavaScript 플러그인을 받지 않는다. Rust로 짠 Wasm 플러그인만 받고, 그건 swc_core ABI가 호스트 SWC 버전과 정확히 맞아야 하며 안 맞으면 빌드가 죽는다 — Next 마이너 버전마다 재빌드·재배포가 필요해진다.

그래서 Next에서는 훅 D가 불가능하고, 컴포넌트 정의 위치를 얻을 수 없다. JSX 호출 위치는 훅 G로 정상 동작한다. 실측 결과 SWC의 __source 줄 번호는 webpack·Turbopack 양쪽 다 정확했다 — 파싱부터 JSX 변환까지 한 패스라 코드가 움직이지 않기 때문이다.

3브라우저 런타임 — 정보가 사라지는 순간

// 컴파일 결과 (Babel·SWC 공통, dev 모드)
jsxDEV(Button, { onClick: x }, void 0, false,
       { fileName: "src/App.tsx", lineNumber: 42, columnNumber: 7 },   // ← 여기 있다
       this)
jsxDEV 호출 ★ G __source가 살아있는 유일한 순간 ↓ React element 생성 { type, props, key, … } ↓ Fiber 생성 React 19가 __source를 버린다 (_debugSource 제거) ↓ commit → DOM ↓ … 시간 경과 … ↓ 사용자가 hover → 우클릭 이 시점에 손에 쥔 것: · DOM 노드 → 소스와 무관 · Fiber → type·props·return 있음, 위치 필드 없음 · fiber.type → 컴포넌트 함수 객체. JS에는 함수의 정의 위치를 읽는 표준 API가 없다
그래서 WeakMap이 필요하다

화면에 떠 있다는 건 렌더가 이미 끝났다는 뜻이다. 클릭 시점에는 가로챌 흐름 자체가 없다. __source 객체는 jsxDEV가 리턴하는 순간 참조가 끊긴다.

훅 G는 "미리 해두는 여분의 일"이 아니라 그 사실이 존재하는 유일한 순간에 받아 적는 일이고, 레지스트리(WeakMap)는 캐시가 아니라 렌더 시점과 클릭 시점을 잇는 다리다.

키를 element.props로 잡으므로, 언마운트되어 그 객체가 버려지면 항목도 함께 GC된다. 결과적으로 화면에 살아있는 것만 메모리에 남는다.
