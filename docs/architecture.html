react-code-locator 동작 원리

1.0.0 · "화면의 이 요소, 내 코드 몇 번째 줄이야?" 하나에 답하는 도구 · 이 문서의 모든 경로/한계는 실측 기준

0큰 그림 — 4단계 파이프라인

핵심 아이디어 한 줄: 컴파일러가 dev 모드에서 어차피 만들어주는 위치 정보를, React가 버리기 직전에 가로채 보관해뒀다가, 클릭할 때 꺼내준다.

① 빌드 타임
모듈 바꿔치기
react/jsx-dev-runtime import를 우리 래퍼로 리다이렉트. 앱 코드는 0바이트 수정.
② 런타임
가로채서 보관
jsxDEV 래퍼가 요소 생성 때마다 위치를 WeakMap 레지스트리에 기록.
③ 조회
DOM → fiber → 위치
클릭된 DOM에서 fiber를 얻어 트리를 올라가며 레지스트리를 조회.
④ UI / 에디터
오버레이 → VS Code
호버 하이라이트 + 클릭 시 /__open-in-editor로 에디터 점프.

훅은 단 하나(①)뿐이고, 번들러별 통합 코드는 전부 "그 하나의 훅을 각 번들러에서 어떻게 거는가"의 변주다.

1빌드 타임 — 위치 정보는 이미 공짜로 존재한다

dev 모드에서 모든 JSX는 컴파일러(Babel/SWC/esbuild)가 이렇게 바꾼다. 5번째 인자를 보라 — 파일·줄·칸이 이미 실려 온다.

// 내가 쓴 코드
<button className="btn">저장</button>

// 컴파일 결과 (dev)
import { jsxDEV } from "react/jsx-dev-runtime";  // ← 컴파일러가 자동 삽입
jsxDEV("button", {...}, key, false,
  { fileName: "src/App.tsx", lineNumber: 42, columnNumber: 7 },  // __source
  this);

문제는 React가 이 __source를 받자마자 버린다는 것(React 19는 아예 보관 필드를 삭제했다 — DevTools 소스 표시가 19에서 사라진 이유이자 이 패키지가 존재하는 이유). 그래서 React에게 전달되기 직전 지점, 즉 jsxDEV 함수 자체를 우리 것으로 바꾼다.

바꿔치기 전략 A — Vite: importer를 아는 리다이렉트

vite.ts · resolveId 훅
앱 코드의 import "react/jsx-dev-runtime"→우리 래퍼 모듈로 리다이렉트
래퍼 자신의 import "react/jsx-dev-runtime"→통과 (진짜 React 런타임)
Vite의 resolveId(specifier, importer)는 누가 import했는지 알려주므로, 래퍼 자신만 예외 처리하면 끝. 파일 생성이 전혀 없다.

바꿔치기 전략 B — webpack · rspack · Next · Turbopack · esbuild · rollup: 생성된 shim

이들의 alias는 specifier 문자열만 보고 무조건 바꾼다. 순진하게 alias를 걸면:

순환 문제
앱 → "react/jsx-dev-runtime"→우리 래퍼→래퍼 → "react/jsx-dev-runtime"→다시 우리 래퍼 (∞)

탈출구: 설정 시점에 Node로 진짜 런타임의 파일 경로를 미리 찾아두고, 그 경로가 하드코딩된 shim 파일을 생성해 alias가 그걸 가리키게 한다. 경로로 require하니 alias에 다시 걸릴 일이 없다.

// node_modules/.cache/react-code-locator/  ← 매 부팅마다 재생성
├── jsx-dev-runtime.js   // 아래 내용의 shim
├── wrap.js              // 래퍼 본체 복사본 (모노레포/링크 대응: 형제 파일만 참조)
└── package.json         // {"type":"commonjs"} — 프로젝트가 "type":"module"이어도 CJS 유지

// jsx-dev-runtime.js (생성됨)
const real = require("../../react/cjs/... (실제 경로)");   // 경로 require → 순환 불가
const { wrapJsxDev } = require("./wrap.js");
const options = { projectRoot: "/Users/me/my-app" };        // 빌드 머신에서만 아는 값을 여기서 굽는다
exports.Fragment = real.Fragment;                             // 정적 exports — webpack이 named export를 인식
exports.jsxDEV = wrapJsxDev(real.jsxDEV, options);
shim의 디테일없으면 생기는 일 (전부 실전에서 발견)
.js 확장자 (.cjs 아님)CRA의 catch-all file-loader가 .cjs를 정적 애셋으로 번들 → jsxDEV가 URL 문자열이 됨 (경고 3,025개 + 크래시)
package.json {"type":"commonjs"}프로젝트가 "type":"module"이면 shim이 ESM으로 해석돼 module is not defined로 즉사
정적 exports.x = 대입module.exports = wrap(...)이면 webpack이 named export를 못 봐 JSX 파일당 경고 1개씩
ModuleScopePlugin 허용 목록 등록CRA가 "src/ 밖 import 금지"로 shim을 차단 (에러 86개)
상대경로 requireTurbopack이 절대경로 specifier를 거부
Next는 vendored React를 감쌈next/dist/compiled/react 대신 일반 react를 감싸면 React 내부 상태가 둘로 갈라져 첫 렌더에서 사망

2런타임 — 요소가 태어날 때마다 위치를 장부에 적는다

wrap.ts · 요소 1개 생성 시퀀스 (+382ns)
jsxDEV("button", props, …, __source)
↓ ① 경로 정규화: /Users/me/app/src/App.tsx → src/App.tsx (React에 넘기기 전에 — React ≤18의 _debugSource에도 같은 값이 실리도록)
↓ ② 진짜 jsxDEV 호출 → React 요소 생성
↓ ③ 레지스트리 기록
WeakMap: element.props → { file: "src/App.tsx", line: 42, column: 7 }

왜 key가 props 객체인가? React는 요소를 fiber로 바꿔치우지만 props 객체는 그대로 fiber에 실려 다닌다. 나중에 DOM에서 거꾸로 출발해도 도달할 수 있는 유일한 불변 연결고리가 props다. WeakMap이므로 요소가 사라지면 기록도 GC로 자동 소멸 — 장부가 무한히 자라지 않는다.

레지스트리는 globalThis[Symbol.for("react-code-locator.registry")]에 하나만 존재한다. 번들이 여러 개여도(코드 스플리팅, 마이크로 프론트엔드) 같은 장부를 공유한다.

3조회 — 클릭된 DOM에서 거꾸로 걸어 올라간다

사용자가 <input>을 클릭했다고 하자. locate()는:

locate.ts · fiber walk (RemoteCall 로그인 페이지 실측 그대로)
  • DOM <input> → el.__reactFiber$xyz → fiber(input)레지스트리 HIT → src/…/LoginForm/index.tsx:455:21
↑ 만약 여기 기록이 없었다면 (styled-components 내부, 라이브러리 요소 …) fiber.return으로 계속 상승:
  • fiber(styled.input 내부)기록 없음 → 통과
  • fiber(node_modules의 요소)위치가 node_modules → 필터링
  • fiber(<InputLabel> — 내 코드의 JSX)가장 가까운 "내 코드" 위치 반환
각 fiber에서 보는 순서: ① WeakMap 레지스트리에 props가 있나 (주 경로) → ② fiber._debugSource가 있나 (React ≤18 폴백 — classic 빌드의 옛 프로젝트도 이 덕에 동작). node_modules 소속은 걸러서 항상 "내 코드"의 위치를 답한다.
이 "위로 걷기" 때문에 React.createElement/cloneElement로 만든 요소는 null이 아니라 가장 가까운 JSX 조상의 위치가 나온다(실측: 자기 정의 줄 대신 부모 <div>의 줄). 근처엔 떨어지지만 조상 위치라는 표시가 없는 것이 알려진 개선점.

서버 컴포넌트 — 장부에 없는 요소들

서버 컴포넌트의 jsxDEV는 서버 프로세스에서 실행됐으므로 브라우저 레지스트리에 없다. 이 경우 별도 경로(rsc.ts):

locateAsync · owner-stack 경로 (Next 15·16 App Router)
fiber._debugStack (React 19 owner stack — 에러 스택 형태)→번들 위치 추출 (page.js:123:45)→Next 소스맵 서비스로 원본 복원→app/server/page.tsx:13:5
소스맵 fetch가 비동기라 locateAsync로 분리; 한 번 풀린 위치는 캐시되어 동기 locate도 즉시 답한다.

4UI와 에디터 점프

runtime.ts + open-in-editor.ts + dev-server.ts
enableLocator({ triggerKey: "shift" })→shift 누른 채 호버: 오버레이 + "src/App.tsx:42" 라벨
클릭→GET /__open-in-editor?file=src/App.tsx:42:7→서버가 실행: code --goto src/App.tsx:42:7
엔드포인트는 Vite에 내장, webpack/Next에는 우리 미들웨어(openInEditorMiddleware)를 dev 서버에 얹는다. 미들웨어가 없어도 메뉴의 "경로 복사"는 항상 동작.

5지원 매트릭스 — 전부 브라우저 실측

환경경로결과

유일한 실측 구멍: classic + React 19. 가로챌 import가 없고(①) React 19가 _debugSource를 삭제해(②) 위치 데이터가 브라우저에 도달할 방법 자체가 없다. React 19로 올릴 정도의 프로젝트는 거의 automatic이라 현실 빈도는 낮음 — 남은 과제는 이 조합을 감지해 콘솔 경고를 내주는 것.

비용 실측: 요소당 +382ns (10k 요소 렌더에 ~3.8ms) · 빌드 오버헤드 Vite 0.49ms/모듈, 그 외 ~0 · 이전 버전(0.4.x) 대비 dev 코드 증가 +90% → 0~31%
